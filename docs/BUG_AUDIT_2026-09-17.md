## 1. 本轮结论

本轮围绕“大 ZIP 上传慢、上传/标签转换不可观察、刷新误判卡死、训练任务身份不清晰”继续审计，并额外检查了 Linux 无桌面部署、算法 SQL 数据安全、新畅联交互和长期任务运行方式。

当前没有发现需要立刻回滚本轮上传实现的 P0 数据破坏问题。已经发现并修复 4 个真实缺陷：

1. Linux 无可用 Keyring backend 时，读取新畅联公开配置会 500，进而影响页面初始化。
2. ZIP 上传阶段显示 100% 后，进入后台导入会退回 0%/8% 等，整体进度语义错误。
3. 浏览器在分片上传途中刷新后，File 对象已经丢失，但任务中心仍可能长期显示“正在上传”。
4. 续传会话 fingerprint 原先仅由文件名、文件大小、`lastModified` 组成，不同 ZIP 存在理论上的误复用分片风险。

这些问题均已进入永久测试；`ZIP Import Durable Runtime` 在 Ubuntu、Windows、后端持久化和 Real Chrome 刷新恢复链路上通过。

### FIX-01 — Headless Linux Keyring 不可用导致页面配置接口 500

**级别：P0/P1（部署阻断）**  
**状态：FIXED**

### 现象

GitHub Actions Real Chrome 在 Ubuntu 无桌面环境中访问：

```text
GET /api/v63/external-algorithm-platform/config
```

出现：

```text
keyring.errors.NoKeyringError:
No recommended backend was available
```

最终导致页面初始化链路出现 HTTP 500。

### 根因

`KeyringSecretStore.get()` 直接透传 keyring backend 异常；`ExternalAlgorithmPlatformService.public_config()` 只是读取“是否已配置/脱敏标识”，但这个只读请求也会因为系统没有 SecretService/KWallet 等可用 backend 而失败。

### 修复

`platform_core/secrets.py`：

- 新增 `SecretStoreUnavailable`；
- Keyring set/get/delete 的 backend 异常统一转换为明确的 SecretStore 不可用异常；
- `SecretCredentialStore.public_state()` 对只读公开状态安全降级：

```json
{
  "configured": false,
  "masked": "",
  "available": false,
  "error": "SECRET_STORE_UNAVAILABLE"
}
```

- Secret 真正读写仍 fail-closed，不把 AccessKey/AccessSecret 回退保存到 JSON 明文。

**级别：P1**  
**状态：FIXED**

### FIX-03 — 分片上传途中刷新后“假装还在上传”

**级别：P1**  
**状态：FIXED**

### FIX-04 — ZIP 续传 fingerprint 可能误复用另一个文件的分片

**级别：P1（低概率、高影响数据完整性）**  
**状态：FIXED**

### 原实现

```text
filename + file_size + lastModified
```

理论上不同文件可以拥有完全相同的三项元数据。

### 新实现

浏览器对文件头 / 中 / 尾做内容采样，并加入哈希：

```text
v2:<name>:<size>:<lastModified>:<sample-content-digest>
```

有 WebCrypto 时使用 SHA-256；兼容环境有退化 sample hash。服务器最终 assemble 仍会计算完整 ZIP SHA256 和精确字节数。

## 3. 当前上传 / 导入链路事实

### ZIP 网络上传

```text
8 MiB/part
最大并发：4
单分片重试：2
服务端按 part 独立持久化
```

## 4. 已确认不是当前 BUG、不要重复重做

### CLOSED-01 — 算法 JSON 全量覆盖问题

当前正式功能分支已经不是“create/update/version attach 都整表读出再 replace”。

`platform_core/algorithms.py` 的普通变更已经调用：

```text

AlgorithmSqlStore.delete_algorithm
AlgorithmSqlStore.attach_version

```

新畅联同步也走：

```text

```

因此后续 AI 不要再以“算法 CRUD 仍然全量 replace”为前提重新实施一遍迁移。

`save_algorithms()` 仍保留，是兼容入口，不代表主业务 CRUD owner 仍采用 JSON/全表写入。

### CLOSED-02 — 老算法列表会被新畅联同步删除

本地算法与外部算法分来源保存；新畅联下架产品采用 `external_active=false`，保留历史算法与版本。同步不应该删除既有本地算法列表。

### CLOSED-03 — 训练任务 UI ID 与真实后端 ID 不一致

训练弹窗预生成 `train_<hex>` 任务 ID，提交给唯一 `TrainingSubmitRuntime`；后端接收同一个 task ID。重复请求同一合法 ID 时返回原 TRAINING task，避免网络重试制造重复训练任务。

### CLOSED-05 — Multipart session TTL / GC

**级别：P1/P2**
**状态：CLOSED**

当前实现：

```text
默认 TTL = 24 小时
created_at / updated_at / expires_at
part 成功写入后自动续期
completed 上传不参与过期清理
```

`ZipMultipartRepository.cleanup_expired()` 会删除过期未完成 session，并返回 `removed_uploads / released_bytes`。

`cleanup_expired_if_due(interval_seconds=60)` 使用 GC marker 做节流。右下角上传任务中心轮询的 v19 job list 服务端入口会触发该方法，因此平台正常运行时最多每 60 秒执行一次过期扫描；创建/恢复上传时仍有兜底清理。

这一策略参考 resumable upload 的 expiration 设计，但 24 小时是本平台当前产品策略，不是协议强制值。

### OPEN-04 — 新畅联 auto-sync 仍由 Web/API 进程 daemon thread 驱动

**级别：P2，扩展部署前处理**

当前 router 构建时启动 daemon thread，每 30 秒检查是否到期，并使用 FileLock 避免同一共享目录同时 sync。

单进程当前可用，但多 Web worker / 多机 API 部署时会出现多个线程竞争同一个 lock；职责也不应长期属于 Web 进程。

推荐迁入现有 scheduler / durable worker，而不是再造一个新任务系统。

## CLOSED — Training label filter task-derived negatives

2026-09-17 product rule: selected materials stay in the training task. The training label checkbox defines the positive schema. If all source boxes are excluded by that schema, the task projection becomes an auditable background sample (`negative_origin=filtered_by_training_labels`) without mutating source annotations. Mixed-label images retain selected boxes. Explicit `确认无目标` remains distinct.
