## 下一专项：P1 20 万规模训练素材选择器性能与交互

**目的**：在数据正确性已有独立回归的基础上，找出选择器打开慢、筛选翻页慢、批量确认等待以及 20 万素材下的潜在浏览器卡顿的**真实瓶颈**。不预设 Vue/数据库/框架切换，也不凭历史症状猜测当前必然存在某个 Bug。

### 第一阶段：只读审计与测量（优先）

- 复用 `tests/browser/training-material-picker-performance.spec.mjs` 现有真实 Chrome 隔离采样：21 次打开（首轮冷启动 + 20 次暖启动）、60 张当前页、10 张优先解码 192px 缩略图，测点击至已解码绘制、Long Task、请求总数；现有性能报告的数字明确**不是生产 P95**。
- 复用已经存在的 20k/30k 冻结引用浏览器测试及 200k 虚拟素材分页响应，只验证网络/冻结引用是小型 POST，而非让前端下载 200k ID。
- 为高价值交互补独立诊断：打开 → 搜索筛选 → 分页 → select-filtered → 确认草稿；分别观察 API 耗时（浏览器模拟值与服务器值区分）、请求取消/迟到覆盖、主线程长任务、DOM 数量、相同数据重复渲染、缩略图解码等待和可能的缓存复用问题。
- 查 `static/modules/training-material-picker-runtime.js` 的事件绑定、分页缓存、filter 状态和 `bulkPending`，再对照服务端 `training-materials` 接口有没有不必要的全量统计或重复扫描。需要源证据才可下 Bug 结论。

### 第二阶段：由证据决定最小修复

- 如果是前端大量 DOM 或重绘：针对已证明的重复渲染/不可见图片工作精准收敛；不主动换 Vue 或重写模块。
- 如果是 API / 统计链：首先证明慢点在服务端及可避免的计算，继续采用分页、按需统计和过期请求隔离等成熟做法，不迁移数据库、不改全站 app.py。
- 如果是网络/图片解码：按真实指标决定请求去重、可视图加载和失败降级，不破坏跨页选材、冻结引用或标签合同。
- 如现有孤立 Chrome 采样已经达标、没有可证异常，**不为“优化”制造无用重构**；记录数据并转下一项。

### 验收 / 风险控制

1. 所有功能变更必须有对应回归：选中数量、跨页选择、冻结引用、取消、迟到响应、确认后草稿入选；只有修复根因才调整代码。
2. 使用隔离数据源测量，记载 P50/P95、样本量、环境与冷/暖差异；不用未经核实的任意生产指标为验收结论。
3. 精准提交至 `feature/external-algorithm-publishing`，准确 SHA 的 CI 全绿后才能称代码验收；任何 P1 性能数据均不代替 P0-06C 生产任务对账。
4. 不操作 A800/4070、不创建/中断训练、不动 GT、不合并 main、不发 Release。
