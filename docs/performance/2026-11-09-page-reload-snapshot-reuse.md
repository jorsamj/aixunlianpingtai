# 2026-11-09｜P0 整页刷新、算法版本与训练列表快照复用

## 问题与审计证据

用户反映 F5 后反复看到「基础列表已就绪，共 110 个算法；完整版本和训练统计正在读取」，随后算法列表与训练历史要等待很久。此前 4070 有算法、任务接口几十秒的观测，但本轮未连接生产测量，不将现场延迟直接归因于某一个函数。

长期分支在修复前存在以下真实代码路径：

1. `static/app.js::__clInit` 每次浏览器 reload 均等待 `/api/v53/bootstrap/snapshot` 后首次绘制。服务端 `_V53_BOOTSTRAP_SNAPSHOT` 虽有 revision 缓存，浏览器没有跨 F5 的上次可信视图。
2. `app.py::_v53_build_core_snapshot` 默认只给 110 个基础算法，固定 `algorithms_deferred=True`；进入算法页后 `AlgorithmListRuntime.refresh()` 再读取 `/algorithms?summary_only=true` 的全部版本卡片。后端已做 SQL `json_extract` 窄投影，但每次 F5 后独立请求仍须重复重建该投影。
3. `TrainingTaskRuntime.refresh()` 进入任务页读取原完整 `/jobs`，历史投影可能昂贵；同时任何一次查询完成都会把算法快照时间设零，连纯运行进度更新也会造成返回算法页时重查。
4. 原任务的实时状态、创建恢复、版本安全校验和手工刷新必须仍由现有 API/Worker/Task Owner 提供，不能用过期浏览器视图绕过正式校验。

## 本次修改

- **保留同一个服务器快照 Owner**：`/algorithms?summary_only=true` 在项目 ID 和 `algorithm_revision` 一致时直接重用已有 `_V53_BOOTSTRAP_SNAPSHOT.algorithms`。首次构建成功后原位将紧凑版本卡片填进 v53 core 快照。并发写入前后再次核实 SQL revision，变化则绝不发布旧卡片；完整详情 API 和版本报告不变。
- **保留同一个浏览器启动 Owner**：`static/app.js` 使用 tab 级 `sessionStorage` 保存一个有界的上次展示快照，最多 2 MiB，最长 24 小时，并由现有 app.js URL 构建标识隔离。仅保存项目/标签/算法卡片、材料统计和有限的任务展示字段；不缓存密钥、模型配置凭据、正式 GT、原图或报告全文。浏览器 F5 先绘制这份上次视图，不等待网络；随后原 v53 请求后台验证，revision 不变继续复用，变化即调用原 AlgorithmListRuntime 加载真实卡片。无存储许可、首次访问或超额时走原完整安全启动流程；超额退回基础卡片，不留下旧的“假新鲜”视图。
- **训练任务分时复用**：无活动任务且已有最近可信任务视图时，页面再进入／F5 最多复用 2 分钟；存在排队、运行、暂停等任务仍用原 5 秒页内节流和原 SSE/PollRegistry 实时更新。手动刷新与任务创建、暂停、停止、恢复后的强制查询仍访问真实服务端。只有新增或已结束任务状态变化时才使算法版本快照失效；纯 Epoch/进度更新不使算法卡片重查。
- **兼容性**：无新数据库、定时任务、网络请求中心或第二套业务缓存；无版本号 `VERSION.txt` 变化，不修改 4070/A800 数据，不部署。

## 验收合同

| 场景 | 预期 |
| --- | --- |
| 同一浏览器 tab 首次打开 | 没有可信会话快照，沿用原 v53 安全启动 |
| 已加载完整算法卡片后按 F5 | 先显示上次卡片，不等算法与任务历史 HTTP |
| 后端算法修订号不变 | 旧完整版本卡片保持，后端 API 直接命中原 v53 缓存 |
| 算法修订号改变 | 旧卡片失效，调用原算法列表接口重新读取 |
| 同步刷新运行中任务 | 按原 PollRegistry/SSE 更新；不误用 2 分钟终态 TTL |
| 训练进度变化但未完成 | 不反复重查整个算法版本图 |
| 训练完成／新增终态 | 使算法卡片查询失效，以便获取新版本真值 |
| 手动刷新任务/算法 | 仍请求服务端，不能被跨 F5 缓存吞掉 |
| 缓存超额／损坏／跨构建 | 退回原启动，服务端 truth 不变 |

## 测试与遗留风险

- 受控 Python API：`test_bootstrap_core_lifecycle` 已新增同 revision 复用、变 revision 失效回归；与 bootstrap 标签真值、任务状态、SQL 应用合同合计 **27/27 通过**。
- 受控 Node：新增模拟浏览器 F5 的“先展示、后等待服务器”及 revision 变化测试；补训练终态 TTL 与运行中进度失效边界。全部前端单元/合同集 **1576/1576 通过**；`node --check`、`python -m py_compile`、`git diff --check` 通过。
- GitHub Actions、真实 Chrome 和真实 4070 20 万规模的冷/温 P50/P95：须以本批实际 commit SHA 的 CI 和现场独立核验结果为准，不能将合成测试冒充现场性能。
- 服务端 `_V53_BOOTSTRAP_SNAPSHOT` 仍是单进程内存，Web 服务重启或多进程首次命中仍会有一次紧凑 SQL 建立成本；未引入额外磁盘快照系统。
- 前端会话数据是**上次展示值**，不是任务准入或写入凭据。跨 tab 新建终态任务最多可能晚 2 分钟自动显示，用户可随时手动刷新；训练动作始终由服务端确认。
- 训练任务完整 `/jobs` 历史查询本身仍是独立的服务端 P95 待办。本批实现的是快速重现与避免无意义重复查询，不声称消灭历史第一次慢查询。
