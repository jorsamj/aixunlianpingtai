> **定位**：这是判断"性能整改是否真正有效"的**统一标准**，不是一次测试报告。

> **当前状态**：本规范是**新提出**的验收方法。仓库中已有的全部性能数据都是**隔离环境结论**，生产性能为 `NOT VERIFIED`。

> **标识约定**：`MEASURED` 已有实测且可复核；`NOT VERIFIED` 无证据；`PROPOSED` 建议值、**未经用户签认**；`TBD` 待确定。

## 1. 目的与适用边界

### 1.1 目的

1. 让"20 万素材是否流畅"从主观描述变成**可复核的判定**。
2. 让每次性能整改必须提供**同环境前后对比**，而不是单次毫秒数。
3. 让"隔离测试通过"与"生产验收通过"在文档层面**永久分开**。

### 1.2 适用

- 素材库、素材选择器、AI 审核、正式 GT 入库、训练创建/准备、任务列表、批量治理。
- 任何声称"解决 20 万级性能问题"的改动。

### 1.3 不适用

- GPU 训练吞吐、模型转换速度、硬件推理精度——属于训练/转换验收，不在本文。
- 功能性正确性——属于各业务合同与定向测试，不在本文。

### 1.4 三条硬规则

1. **隔离测试不能叫生产 P95。**
2. **单次或 7 次最大值不能叫 P95。**
3. **没有签认阈值、样本不足、拿不到关键数据 → 只能写 `NOT VERIFIED`，不能写"通过"。**

## 4. 数据规模与代表性

### 4.1 规模档位

| 档位 | 素材 | 算法 | 版本 | 历史任务 | 用途 |
|---|---:|---:|---:|---:|---|
| S | 1 万 | 20 | 100 | 200 | 功能回归与快速迭代 |
| M | 5 万 | 60 | 500 | 500 | 中期验收 |
| L | 20 万 | 110 | 1,100 | 1,000 | **主验收规模** |
| XL | 50 万 | 110 | 1,100 | 2,000 | 容量边界（可选） |

**规模之外必须同时控制比例**，否则数字不可比。下表的比例只作为**合成压力测试建议**，不得替代真实分布：

| 维度 | 建议代表性 | 说明 |
|---|---|---|
| 标注覆盖率 | 60%–85% 已标注 | 过低会让 GT 谓词"太快"，过高会让稀疏路径消失 |
| 零框确认比例 | 5%–15% | 影响 `confirmed_empty` 分支 |
| 多标签比例 | 20%–40% | 影响 `label_mode='all'` |
| 长尾类别 | 至少 3 个类别占比 < 0.5% | 这是稀疏路径的真实来源 |
| 负样本池成员 | 5%–15% | 影响池过滤与历史排除 |
| 已用于训练比例 | 10%–30% | 影响 usage 反连接与历史资格 |
| 图片尺寸分布 | 小/中/大三档各 ≥20% | 影响解码与缩略图 |
| 存储类型 | 至少一档使用远程（OSS/NAS） | 只测本地会低估 IO |
| 历史任务年份 | 至少跨 2 个版本周期 | 影响兼容分支 |

### 4.2 数据来源与代表性

1. **首选脱敏真实数据**：以真实项目的素材、GT、标签、历史使用与负样本分布为准；4.1 的比例只用于核对"是否明显偏离"，不作为构造目标。
2. **合成数据仅用于压力测试**：按 4.1 比例构造时必须标注"合成"，并说明与真实分布的差异；其结论不得写成"生产代表性"。
3. 必须记录：真实图片数、尺寸/格式分布、来源、GT 状态、算法与负样本比例、磁盘与网络。
4. **不得**只用"高度规则化的 ID + 小元数据"就宣称代表生产；也不得用合成结果覆盖真实数据结论。

## 6. 指标分层

### 6.1 浏览器端

| 指标 | 说明 |
|---|---|
| 可见内容时间 | 从导航到用户看到真实数据（不是骨架屏） |
| TTFB | 首字节时间 |
| 下载与解码 | 响应体大小、图片解码耗时 |
| Long Task | >50ms 的主线程任务数量与总时长 |
| 交互到下一帧 | 点击/勾选/翻页到界面响应 |
| 跨页勾选响应 | 单张勾选 → 复选框与已选计数更新完成 |
| 筛选切换响应 | 条件变更 → 新结果可交互（含取消旧请求） |
| 页面切换响应 | 导航 → 目标页可交互；旧请求不得覆盖新页 |
| 请求数与重复请求 | 同语义请求是否重复 |

### 6.2 API

| 指标 | 说明 |
|---|---|
| P50 / P95 / P99 | 按第 7 节口径 |
| 成功率 / 错误率 | 4xx/5xx 分开 |
| 响应字节 | 大响应必须单独记录 |
| 超时率 | 客户端与服务端分别记录 |
| 关键参数 | 页大小、筛选、修订号 |

### 6.3 数据库

| 指标 | 说明 |
|---|---|
| 单请求 SQL 数 | 识别 N+1 |
| 扫描行数 / 返回行数 | 识别全表扫描 |
| `EXPLAIN QUERY PLAN` | 是否命中索引 |
| 写锁等待 | `busy` 重试次数与时长 |
| WAL 大小 | 写放大 |

### 6.4 存储

| 指标 | 说明 |
|---|---|
| 原图/缩略图读取耗时 | 本地与远程分开 |
| 字节吞吐 | 首屏总下载量 |
| 失败与重试 | 慢节点、权限、损坏 |

#### 6.4.1 缩略图冷态与暖态分别定义

| 组 | 定义 | 必须记录 | 不得混用 |
|---|---|---|---|
| 冷 | 缓存文件不存在或指纹不匹配，需要生成 | 生成耗时、原图读取字节、解码耗时、写入字节、失败原因 | 冷态不要求命中率 |
| 暖 | 缓存已存在且指纹匹配 | 命中率、校验耗时（例如整文件哈希）、锁等待、传输耗时 | 暖态命中率不得作为冷态验收要求 |

**注意**：当前命中路径每次仍会校验缓存文件摘要（`storage/cache.py`），因此"暖态"不等于"零 IO"；验收必须把校验成本算入暖态指标。

### 6.5 Worker

| 指标 | 定义 |
|---|---|
| 排队时长 | **任务具备领取资格 → 实际被 claim**，不是 claim 之后。`eligible_at` / `claimed_at` 是**建议观测时点，不是当前任务表的现成字段**；若现有事件日志/心跳无法提供，需后续单独设计最小埋点，**不得虚构已有采集能力** |
| 启动耗时 | **claim → Handler 开始执行**（进程/上下文准备） |
| 执行时长 | Handler 开始 → 结束，按阶段细分 |
| 重试次数 | 是否退避、退避曲线、是否触达上限 |
| 失败与恢复 | 错误码、是否可恢复、恢复后是否重复写 |
| 积压 | 队列长度随时间 |

**为什么区分**：排队反映容量与调度，启动反映进程/环境，执行反映业务；三者混在一起会误导优化方向。

### 6.6 写入类场景的时间分解

写入类操作（100 张正式 GT、2 万张训练提交、训练 Prepare）必须拆成四段，不得只报一个"总耗时"：

| 阶段 | 定义 | 观测点 |
|---|---|---|
| HTTP 受理 | 请求到达 → 返回受理响应（200/202） | API 日志、`Server-Timing` |
| 排队 | 任务具备领取资格 → 被 claim | Task DB 时间戳 |
| 后台执行 | Handler 开始 → 完成/失败 | 任务阶段与心跳 |
| 端到端 | 用户点击 → 终态可见（轮询/推送可见） | 浏览器时间线 |

**判定**：受理慢属于 API/DB 问题；排队久属于容量问题；执行慢属于业务实现；端到端慢可能只是前端轮询间隔。四者的修复方向完全不同，不能用一个数字代替。

## 7. 统计规范

### 7.1 分位算法与样本量

- 必须写明算法，例如 **nearest-rank**：`P95 = 第 ceil(0.95 × N) 个升序样本`。
- **禁止**用"7 次最大值"标注为 P95；样本不足时直接写"最大值"。
- P50/P95：N ≥ 30 时报告；N < 30 只报中位数与最大值，并标注"样本不足"。
- **P99 不做小样本推断**：建议 N ≥ 300；N 不足时不得报 P99，只能写"样本不足以估计 P99"。
- 即使 N 达标，也必须记录统计局限：单机/单时段、非随机抽样、尾延迟受偶发 GC/IO/网络抖动影响、是否包含重试。
- 必须写明样本数 N 与样本定义（一次请求、一次操作，还是一次任务）。
- 失败样本不得剔除；超时按最坏值计入或单独统计。

### 7.2 冷/热

| 组 | 定义 | 必须记录 |
|---|---|---|
| 冷 | 新浏览器上下文 + 应用缓存未命中；不清 OS 磁盘缓存（除非明确声明） | 冷的是浏览器缓存、应用缓存、DB 还是缩略图 |
| 暖 | 明确预热条件与命中依据；复用相同筛选、排序、页大小、修订 | 命中证据 |

### 7.3 不可比规则

- 不同 SHA、不同数据规模、不同机器、不同网络的结果**不得相加或直接比较**。
- 同一场景的"前后对比"必须同 SHA 之外的一切条件一致；否则只能定性。
- 合成数据与真实数据的结果**不得混在一张表里**当作同一结论。

### 7.4 每次测量必须记录的元数据

```text
SHA / 分支 / 构建产物标识
数据规模与代表性（第 4 节）
机器：CPU、核数、内存、磁盘类型
浏览器与版本、视口
网络：本地/内网/公网、带宽、RTT
数据库：SQLite 版本、WAL 状态、库大小
并发：用户数、后台任务
采样：N、冷/热、起止时间
```

## 10. 执行与安全边界

### 10.1 生产环境

**只允许**：已授权的**只读观测**——现有监控、只读 HAR、`Server-Timing`、只读 SQL 计划、日志采样。

**禁止**：压测、批量写入、故障注入、重启服务、修改数据、触发训练/转换/发布。

**"只读"接口的陷阱**：`GET /api/projects/{pid}/images` 会为缺 `size_bytes` 的素材回写元数据（`app.py` 的 `list_images`），因此它**不是无副作用只读接口**。生产核验必须遵守：

- **不得为测试主动调用**该类 GET 接口去"复现"或"采集"。
- 只能观察正常业务已经产生的既有日志、监控与**经授权**的浏览器 HAR。
- 任何需要主动发起请求的复现，**必须在隔离环境**进行。

### 10.2 隔离环境

写入、取消、恢复、故障注入、2 万冻结与提交、批量治理，**全部在隔离环境**执行：

- 独立项目或脱敏镜像；
- 独立数据库与存储；
- 独立 Worker；
- 明确的生命周期与清理方式。

### 10.3 证据处理

- 归档前删除授权头、Cookie、原图、签名 URL、内网地址。
- 保留：时间/时区、版本 SHA、脱敏项目与请求 ID、修订号、视口、测试条件。
- 脱敏 HAR、Chrome trace、服务器分段指标。

### 10.4 不得做的事

- 为了"跑出好数字"降低页大小、跳过 GT 校验、关闭历史资格。
- 把隔离结果写进对外 SLA。
- 用平均值掩盖尾延迟。
- 用"重跑一次更快"替代样本统计。

## 11. 判定规则

### 11.1 单场景

| 判定 | 条件 |
|---|---|
| `PASS` | 阈值已签认 + 样本量达标（建议 ≥30/组）+ 冷热分组齐全 + 功能断言成立 + 无超时/失败掩盖 |
| `FAIL` | 上述任一项不满足，且**证据有效**、已排除环境噪声；必须附最小复现 |
| `NOT VERIFIED` | 阈值未签认、样本不足、缺关键数据、环境不可比 |

**判定优先级（从高到低）**：

1. **证据不足 → `NOT VERIFIED`**（不是 FAIL；没测不等于不达标）。
2. **证据有效但不达标 → `FAIL`**（必须附数据与最小复现）。
3. **证据完整且达标 → `PASS`**。

不得用 `FAIL` 表达"没测到"，也不得用 `NOT VERIFIED` 掩盖"测了但不达标"。

### 11.2 两个验收层级（不得互相替代）

**L1：20 万素材浏览与选材性能达标**

覆盖 M01–M11 中与浏览、筛选、分页、选择、冻结、训练创建相关的场景。条件：

1. L 档（20 万）对应场景 `PASS`。
2. 冷/热两组均达标（缩略图按 6.4.1 冷热分列）。
3. 无 P0/P1 功能回退。
4. 关键路径 SQL 计划有证据（无意外全表扫描）。
5. 失败率与超时率在签认预算内。
6. 结果表完整填写，含 SHA、环境、N、口径。
7. 由用户或授权现场负责人签认。

**L2：完整算法生产平台全链路验收**

L2 必须先声明**验收范围**，逐项列出"必需项"与"排除项"；不允许用"可选"含糊带过。

| 业务链 | 是否必需（按本次范围填写） | 说明 |
|---|---|---|
| 素材浏览 / 选材 / 训练创建 | 必需 | 与 L1 相同 |
| AI 审核 → 正式 GT 批量入库 | 由范围决定 | **若列入必需项，C2-B 必须先收口并通过定向测试**；不得写成"可选" |
| 训练 → 评估 | 由范围决定 | — |
| 模型转换 → 异构部署 | 由范围决定 | 需真实硬件证据 |

要求：

1. 范围表已填写并由用户签认。
2. 必需项对应场景 `PASS`；排除项必须写明排除理由与遗留风险。
3. **若"正式 GT 批量入库"被列为必需业务，C2-B 未收口则 L2 直接判 `NOT VERIFIED` 或 `FAIL`**，不得以"可选"继续。
4. 真实硬件/转换验证有独立证据。
5. 签认。

**规则**：

- L1 通过**不等于** L2 通过；L2 未完成**不应阻止** L1 独立验收，只要在结论中列明未覆盖范围。
- 任一未覆盖项必须在结论里显式列出，不能默认通过。
- 不得用"某个可选业务未完成"作为否决全部已完成链路验收的理由；也不得用 L1 通过掩盖 L2 缺口。

任一条不满足 → 只能写 `NOT VERIFIED` 或 `FAIL`，并保留真实观测值。

### 11.3 与整改的关系

- 整改必须提供"同环境、同数据、同 SHA 之外条件一致"的前后对比。
- 只报"改后更快"而不报"改前基线"的，不予采纳。
- 结构推断（"这个文件很大所以慢"）不能替代测量。
