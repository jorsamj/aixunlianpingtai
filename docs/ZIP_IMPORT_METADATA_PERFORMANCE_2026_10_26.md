## 需求与现状

用户现场在标签转换/写入阶段约1.5–3秒/图；这是现场反馈，不是本轮测量。当前add_image_record → _v50_assert_dataset_writable_locked → _v50_recover_dataset_deletions → _v50_clear_orphan_dataset_delete_claims，即使无删除标记仍MaterialRepository.read全量SELECT/fetchall并解析。YOLO/COCO/VOC和普通图片写入共享此路径。异常路径随后mutate还会全量读取一次。

原v19持久后台任务、队列、批量素材事务、YOLO/COCO/VOC最终GT写入、AnnotationRepository、StorageManager原子复制及同程SHA256、Worker按需物化与TrainingBundleCache继续复用。不得以这条热点解释所有生产耗时，也不预先承诺倍数。

## 设计与取舍

1. 先用真实隔离本地文件、原YOLO转换/批量提交链建立A–D基线及阶段聚合。历史存量为合成元数据，新增图片为真实小图；必须标记为隔离微型图片集成基准，不能当生产速度。原ZIP传输/解压不在标签转换计时内，另记录完整被测转换及提交时间。
2. 优先采用用户方案二：在原materials.payload_json的删除标记上建稀疏SQLite表达式索引，只读取有标记的候选。JSON是唯一字段Owner，不复制删除状态，不建缓存。按原Python数据集/有效token语义筛选，在原仓库事务内只改确认为孤立的行。
3. 保留每张写入、最终提交前的原数据集FileLock、恢复journal、活动token和存在性校验。全项目恢复发现也只查有标记的候选。EXPLAIN验证访问稀疏索引；旧schema一次升级，现有初始化锁和user_version快路复用。
4. 不采用跨进程缓存或仅批量开始检查：容易遗漏并发删除。仅加普通dataset索引但仍解析全体JSON不能解决本热点。索引升级只构建元数据索引，不迁移图片或GT；首次构建耗时与重复启动分别验证。
