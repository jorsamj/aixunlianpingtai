# 42.24.517｜训练资源创建恢复与冲突素材原图回收

## 用户实际需求与截图证据

1. 「同图不同标注」批量治理要有**真实原图物理回收**路径，不能只删正式 GT、索引和旧标注文件；但保留项仍依赖的同一份物理源文件、历史恢复及活动任务绝不误删。
2. 训练创建第 2 步弹窗经常提示「训练资源尚未就绪，请等待或重新读取配置」，页面隐藏训练资源下拉框没有有效 target；用户需要自动恢复并知道真实阻断原因。

## 训练资源 P0 根因和本批修复

- 旧 `training-create-hydration.js` 即使 `/api/training_options` 只返回 `warning/offline` 或目标列表为空，也记录五分钟缓存时间；后台页面重新赋值 `state.targets=[]` 后，`fresh` 仍可能直接复用空列表。创建弹窗的隐藏 `tr429Target` 只能渲染 `status=ready` 目标，导致前端统一给出无意义的「资源未就绪」，并不等同 GPU 内存不足。
- 改成只有 `trainingOptionsHydrated()` 真正找到已就绪目标/算法时才能复用缓存；空列表、warning、离线状态不缓存为成功。`hydrateCommon` 同样核对当前列表而非单独信任时间戳。
- 提交时若真实选择缺失，在现有 Hydration Owner 中合并进行中的同项目请求或定向强制重新读取一次，等结果返回、校验仍属本窗口/项目/Task 后更新原有资源控件；网络失败、无有效算法、权重配置缺失、节点离线分别给出具体原因。不增加第二套资源 Owner，不循环盲重试，也不伪装 `ready`。
- 页面 Extras 不得在当前训练弹窗覆盖专门的资源加载结果。用户有有效资源时不做新增请求；无资源仍不能绕过后端资源与母模型的严格校验。

## 原图物理回收：清晰的执行边界

- **在线 `DELETE_INDEX` 仍然只删除素材索引与正式 GT，并保留不可变的 `material_retirements` 退出回执。** 不能在线直接 `unlink`：同 SHA 不代表不同物理文件，部分重复素材共享同一个 `object_key`，保留项/训练/评测/历史 Snapshot 可能仍要读原图。
- 用户要求的真正删除由**原有** `LocalMaterialReclamationService` 执行。扩展原 `tools/reclaim_retired_original.py --batch`，按单个删除任务分页（每次最多 50 条）选择已退休的当前素材，先逐张预览路径/进程/存储类型/文件哈希/引用/任务/恢复依赖，再使用与预览完全一致的批量 SHA256 摘要、精确确认文字、稳定操作 ID 和真实操作者执行。每张图片继续复用原 `service.apply()` 的加锁、先记回执、detach→unlink→审计恢复机制；部分失败明确显示，不自动越过检查。
- 本地固定盘 `default_local` 项目 `uploads/` 中可证明无共享引用的 JPEG/PNG 等原图才可进入物理回收；**正在使用的共享原图、未知旧索引、NAS/OSS/S3、自定义存储根、文件身份变化、Web/Worker/Agent 在线或消费者不明，一律拒绝回收并保留原图**。不得把索引退休张数写成真正的物理文件/释放字节数；实际磁盘释放量仍需系统观测。
- 原工作台的任务文案和批量删除预览现在明确提示「删除索引、GT」与「离线原图回收」的区别，并显示该任务 ID 供运维批次引用，不设计在线硬删除按钮。在线完成后 `reclaimed_bytes=0` 不变。

### 运维使用（不代表已授权对生产删除）

应在另行批准的停服维护窗口先做备份、核对生产正在运行的服务及受控本地存储。原工具默认只读。以下参数均为占位，切勿直接填入生产执行：

```bash
python tools/reclaim_retired_original.py \
  --data-dir <独立已确认的数据目录> \
  --project <项目ID> --retirement-task <冲突删除任务ID> \
  --batch --limit 20 --controlled-local-writers
```

只读输出包括 `eligible`、`blockers`、`next_cursor`、`expected_batch_digest`、`required_confirmation`。正式执行必须另行提供 `--apply --expected-batch-digest <预览SHA> --confirm <完整精确确认文字> --operation-id <稳定唯一ID>`，同时由受控维护进程配置 `MC_CONTROLLED_LOCAL_MATERIAL_GC=1`；一页完成后按原样使用下一页 `--after <next_cursor>`。任何新引用或指纹变化会拒绝执行；已离线删除的物理源不在 Web 请求里自动恢复或继续删除。

## 验收矩阵与边界

- 本地前端完整 Node 回归 **1518/1518 通过**；原图回收原有与新增单测合计 **20/20 通过**；脚本编译与 Git 差异空白检查通过。真实浏览器/Chrome 与远端 CI 仍待验证。
- 空资源、只有 warning 的资源不会进入五分钟“可用缓存”；同一项目恢复后自动重新读取，外部页面重置列表仍会补读。
- 创建训练提交前缺隐藏 target 会补一次资源读取；已有真实 `ready` target 维持原提交链路；没有可用权重或资源时继续拒绝提交并给出实际原因，不下发假任务。
- 批量原图回收：默认预览、游标边界（1–50）、共享引用跳过、摘要变化拒绝、精确确认、逐张稳定操作身份和失败回执。新单测使用隔离伪服务证明未确认前不调用物理删除；原 `LocalMaterialReclamationService` 既有安全测试保持不变。
- **尚未进行任何正式项目的物理文件删除、生产服务停机、生产资源重新检测或 GPU/OSS/NAS 真实验收。** 新 SHA GitHub CI、真实20万素材耗时与停服维护演练待后续单独核验；不能把源文件保存逻辑删除的成功误称已释放磁盘空间。
