# 42.25 YOLO ZIP 大规模导入进度

> 目标：10k 真实可用；50k/100k 不出现架构性退化。不要把 CI/synthetic smoke 等同于真实 10k/50k/100k 完整导入验收。

## 已完成的 scale-oriented 改造

1. Durable Storage Worker 路径已存在，`server_zip` 不在 FastAPI 请求线程中执行解压/扫描/索引。
2. YOLO discovery 对常规自包含 ZIP 只 inventory 新 ZIP 的 `target_prefix`；只有 YAML 实际引用 prefix 外部内容时才回退 full-source inventory。
3. Local Storage 新增 cheap metadata inventory：目录枚举阶段不预先 SHA256 全部 image/txt/yaml；真实图片候选在后续 inspect 阶段再 hash/verify。
4. Local image inspect 使用有界并发，默认 `min(8, cpu_count)`，上限 16；远程 Storage Provider 保持串行，避免误把 SDK/网络连接当作线程安全。
5. ZIP durable checkpoint 从“每个完成 member 重写一次不断增大的 completed map”改成 member-count/time bounded checkpoint（默认 8192 members / 30s）。
6. Storage role 已切换到 `platform_core.storage.optimized_import_tasks.OptimizedStorageImportHandler`：ZIP progress callback 的 SQLite heartbeat 和 cancel poll 被节流，避免 50k/100k small-file archive 产生同数量级 Task DB round-trips。
7. 定向 CI 覆盖：self-contained prefix 不重复全盘 inventory、cross-prefix 显式 fallback、local inventory 不 hash、50k progress callback 不按 member 写 task DB。
8. `scripts/benchmark_yolo_zip_scale.py` 可在 Linux 真实 ZIP/真实已解压 YOLO 数据集上分阶段测 `extract / prepare / image verify+sha / annotation scan`。

## 已确认的当前关键缺口

### 1. 浏览器 ZIP 上传仍走 legacy v19 路径（P0）

当前可见 UI 的 `doUploadZip426()` 仍调用：

```text
POST /api/v19/projects/{project_id}/datasets/default/import/jobs
POST /api/v19/projects/{project_id}/import/jobs/{job_id}/start
```

后端 `v19_start_import_job()` 仍创建 daemon `threading.Thread(target=v19_import_worker, ...)`，而 `v19_import_worker()` 仍回落到 `_v18_import_yolo()` / COCO / VOC legacy parser。

因此：

- Durable `server_zip`/Storage Worker 的 10k/50k/100k 优化**不会自动覆盖浏览器上传 ZIP**；
- 历史“10,291 张，约 48 分钟”的现象与这条 legacy in-process/thread path 高度一致；
- 不能因为 `server_zip` CI 已通过就宣称用户当前浏览器 ZIP 上传性能已经解决。

下一步必须把浏览器上传改成“HTTP 只负责流式落盘 + 创建 MATERIAL_IMPORT durable task”，上传结束后所有 ZIP validation/extract/YOLO scan/index 都交给 Storage Worker；旧 v19 parser 只保留兼容读取/历史记录，不再作为大 ZIP 主执行链。

### 2. ZIP extractor 仍有每文件 durability 成本（待真实 benchmark 决定是否优化）

`zip_import.py` 为每个解压文件执行 flush/fsync，100k small-file archive 可能成为下一主瓶颈。暂不盲目删除 durability gate。先在 Linux/NVMe 上用真实 ZIP benchmark 得到 `extract_seconds`，若 extraction 明显占主导，再设计 crash-safe batch durability，而不是直接牺牲数据安全。

### 3. Annotation TXT scan 仍主要串行（待 benchmark 决定优先级）

图片 verify/hash 已有界并发；YOLO sidecar TXT parsing 仍按 manifest page 顺序读取。若 benchmark 显示 `annotation_seconds` 占比高，再做 local-only bounded parallel parser + single-writer SQLite batch。

```bash
  --dataset-root /data/datasets/D-Fire_raw \

  --json-out /tmp/yolo-import-dfire.json
```

真实 ZIP：

```bash
cd /data/platform/aixunlianpingtai
/home/vipuser/miniconda3/envs/yolo/bin/python scripts/benchmark_yolo_zip_scale.py \
  --zip /path/to/dataset.zip \
  --work-dir /data/platform-data/bench/yolo-zip \
  --workers 8 \
  --json-out /tmp/yolo-zip-benchmark.json
```

真实验收必须记录：图片数、ZIP/解压后字节、extract_seconds、prepare_seconds、image_inspection.seconds、annotation_seconds、总时长、CPU、磁盘 I/O、Task Worker 是否存活、Web/API 是否仍响应。
