## 已收口 P0

### P0-01 Duplicate / Leakage Component

`platform_core/training_splits.py` 在随机切分前按 `content_sha256`、来源 group / 视频 group、file identity 建立 leakage component：

- exact duplicate + 本次 selected-label GT 相同：稳定 canonical dedupe；
- exact duplicate + 本次 selected-label GT 不同：切分前 fail-closed；
- independent Train/Test 若 SHA、来源组或 file identity 落入同一 component：直接阻断；
- 最终 `_assert_no_leakage()` 继续作为最后防线。

`training_labels.py` 又把 duplicate GT fencing 前移到 durable TRAINING task 创建前，因此不必等 Worker 启动后才看到同类冲突。

定向 CI 已有 Ubuntu/Windows 成功记录。真实 10k/20k 数据规模性能仍需 A800 服务器验收。

### P0-02 Empty boxes 不得自动变 confirmed_empty

`platform_core/annotation_repository.py` 默认规则已改为：有 boxes -> `annotated`；无 boxes 且没有显式状态 -> `unannotated`。

只有人工确认、可信导入等显式路径才能写 `confirmed_empty`，且需要正确 annotation scope。

### P0-03 Rollback 指针接入真实训练基线

`TrainingHandler` 调 `choose_iteration_base()` 时显式传入 `algorithm['current_version_id']`。回滚 V5 -> V3 后，下一次迭代必须从 V3 的 verified train checkpoint 开始；当前版本不可训练时返回 `CURRENT_VERSION_UNAVAILABLE`，不会静默切换到 V5、其他历史版本或母模型。

### P0-04 algorithms.json 跨进程 mutation fence

`platform_core/algorithms.py` 已加入 Windows/POSIX 跨进程 file lock、原子写、per-algorithm revision、expected_revision 冲突检测、同 task_id version attach 幂等，以及只移动 current pointer 的 rollback。

长期仍建议将算法版本元数据迁入事务型数据库，但当前 JSON 路径已具备基本多 Worker 写安全。

### P0-05 Training Version Artifact Manifest

新训练版本来自标准 task artifact 目录时，`attach_version()` 会从该训练任务的 `snapshot.json` / `payload.json` 建立冻结 manifest：

- 模型文件名、size、SHA256；
- framework / task type / input size；
- snapshot_id / parent_version_id；
- source model / parent model SHA lineage；
- num_classes / names；
- stable `label_id`、业务 code、platform class id、task-local YOLO class id；
- manifest 自身 SHA256。

严格迭代选择会校验 manifest 自身 hash、内部标签结构、模型 size/SHA、snapshot/parent 对应关系和父模型 hash lineage。模型被替换、manifest 被篡改、父版本 manifest 消失或标签快照错配均 fail-closed。

`tests/unit/test_algorithm_artifact_manifest.py` 已覆盖 manifest 生成、模型篡改、自身 hash 篡改、snapshot 错配、payload/snapshot label mapping 错配、parent model hash lineage、parent manifest 丢失、idempotent replay 和 replay 后模型损坏。

代码/CI 层已有成功记录；真实 A800 训练产生的 best.pt manifest 一致性仍需服务器验收。

### P0-06 Generic Retry Attempt Audit

原 `TaskRepository.retry()` 会直接把 FAILED/CANCELLED 等旧任务行改回 QUEUED，覆盖原错误、结束时间和执行历史。当前运行时通过 `platform_core/task_runtime/audited_repository.py` 导出的 `TaskRepository` 改为：

- generic retry 创建新的 task_id；
- `retry_of` 指向紧邻的上一 attempt；
- 原 terminal task 行保持不变；
- 原 payload 复制到新 task 的独立 artifact namespace；
- 双击 Retry 时，如果已经存在活动 child attempt，返回同一个 child，不产生并行 sibling；
- 若旧祖先已有结束的 retry child，则要求从最新 attempt 继续 retry，保持线性审计链；
- `POST_PROCESSING_FAILED` 不走 generic retry，继续使用专门的 `retry_post_processing()`，避免重复训练；
- `MATERIAL_BATCH` retry 使用 SQLite backup 克隆冻结的 `selection.sqlite3`，保留 succeeded/failed 状态。新 attempt 的 MaterialBatchHandler 只把 failed rows 重新置 pending，因此不会重复处理已经成功的素材；
- payload 或 MaterialBatch 冻结 selection 缺失时 fail-closed，不创建注定无法执行的新任务。

旧 `tests/unit/task_runtime/test_repository.py` 中“retry 复用同 task_id”的过时断言已同步改为 immutable attempt 语义，并与新增 `tests/unit/task_runtime/test_retry_audit.py` 一同纳入 P0 workflow。

GitHub Actions run `34476902150` 中 Ubuntu 3.12 与 Windows 3.12 的 compile 和 targeted P0 tests 均已成功。真实长任务 crash/retry 的 Linux 端到端行为仍需服务器验收。

### P0-07 Annotation Ground Truth / Stable Label Authority

训练语义现在明确只有一个 Ground Truth 权威来源：`AnnotationRepository`。

- `label_id` 是类别永久语义身份；旧 `label` code 和 `class_id` 只作为可变化的投影。
- 标注写入时，如果已有合法 stable `label_id`，会按当前项目标签 schema 修正陈旧的 code/class projection；不会让旧 class index 覆盖 stable ID。
- 旧标注只有 code 时，在写入路径可升级为项目当前 stable `label_id`。
- 项目已有稳定标签 schema 时，未知 `label_id`、未知 annotation scope 或缺失类别身份的正式写入会 fail-closed。
- AI 标注人工审核会冻结 `review-scope.json`；审核通过后把本次实际检查过的 stable label IDs 合并进正式 `annotation_scope`。
- 人工确认空结果且无其他正式框时，明确保存 `confirmed_empty + scope`；若已有其他类别框，则保留 `annotated` 并合并 scope。
- `aggregate_training_labels()` 的训练标签可用性来自 AnnotationRepository 的 boxes/state/scope；MaterialRepository 的 `labels` / `label_ids` 不能单独让某类别进入训练。
- 回归测试同时验证了反向情况：素材层没有标签 tag，只要 AnnotationRepository 有合法 GT，训练标签仍然可用。

关键提交：`6ed125f`（stable label authority）、`677224a`（写入约束测试）、`b11db68`（Material tag 不得替代 GT）。GitHub Actions run `34481002970` 的 Ubuntu 3.12 compile 与 targeted P0 tests 已全部成功。Windows 当前不作为阻塞验收条件。

## 其他已收口项

### Worker 角色隔离

旧 `task_worker.py --roles all` 会让 import / annotation / video / training / conversion 等长任务共享一个串行 Scheduler。当前实现改为 supervisor 监督多个 role worker，各角色拥有独立执行通道。

子 Worker 使用统一 process identity（PID、create_time、command hash、process group、launch token）管理；父进程退出时使用 `ProcessController` 安全终止对应进程树。

### Deployment Test 子进程生命周期

部署测试已从裸 `subprocess.Popen()` 收口到 durable process identity：启动后绑定进程身份、运行中 heartbeat、Cancel 终止完整进程树、lease/DB 异常不遗留无主推理进程、recovery 只处理身份验证通过的旧进程；已有且验证通过的结果可以恢复提交而不是盲目重跑。

`.rknn/.om/.bmodel` 无真实板卡/runtime 时仍明确标记硬件阻断，不能把“转换成功”和“板端验证成功”混为一谈。

## 真实 Linux/A800 验收边界

GitHub Actions 只能验证代码路径，不等于生产验收。真实 A800 至少还要验证：

- `actual_device` 真正为 scheduler 分配的 A800；
- RAM/SHM guard 在真实 DataLoader worker 数下有效；
- 训练前后源素材 SHA 不变化；
- Train/Validation 运行期间 Test 未物化；
- best 固定后才访问 Test；
- post-processing crash/restart 不会重复训练；
- rollback 后下一次训练实际加载被回滚版本；
- Artifact Manifest 中模型 SHA 与真实 best.pt 一致；
- generic retry 创建独立 task_id，旧失败行、日志、错误和结束时间不被覆盖；
- MATERIAL_BATCH retry 只重试 failed rows；
- 训练标签来自冻结 Annotation GT，而不是素材 tag / 当前项目 class index；
- 10k/20k 真实素材下 split、bundle、任务刷新和导入耗时可接受。

100k 做有界架构验证；百万级未压测前保持“未验证”。
