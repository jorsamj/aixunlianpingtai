# 42.25.0 权威实现路径

## 基线与用途

- 基线：`01636b6` / `VERSION.txt=42.24.0`。
- 开发分支：`feat/42.25.0`。
- 本文只界定 42.25.0 的权威落点和待淘汰旧路径，不改变业务数据。
- `origin/main` 当前实际仍是 42.21.1，因此不能作为本轮代码基线。

## 不可回退合同

1. 训练素材身份只认 `train_image_ids`、`test_image_ids` 或由其冻结的 selection/split manifest；不得恢复 dataset grouping。
2. 外部 `class_id` 只在一次 `import_id` 中有效；正式 annotation 必须引用平台稳定 `label_id`。
3. `annotation_scope` 表示每个标签的完整 Ground Truth 检查范围；boxes 为空不等于全局负样本。
4. Test 自任务创建起写入 sealed Split Manifest，训练运行时只物化 Train/Validation；最终 best 模型确定后才可读取 Test。
5. Training workspace 禁止 hardlink/symlink；第三方训练框架不得反向修改 Storage Source 原文件。
6. 显式 CUDA 不可用时失败或排队，禁止静默改成 CPU。

## 1. 外部素材扫描、映射与正式导入

### 当前权威路径

- 格式/YAML/layout/框解析：`platform_core/storage/yolo_import.py`
  - `discover_yolo_layout()`
  - `YoloImportScanner.prepare()`
  - `YoloImportScanner.scan_annotations()`
- task-owned SQLite candidate manifest：`platform_core/storage/import_candidates.py`
  - `ImportCandidateStore`
  - `selection_facts()`、`confirm()`、`pending_index_batch()`、`mark_indexed()`
- 用户确认：`platform_core/storage/import_confirmation.py::confirm_import()`
- Durable Worker：`platform_core/storage/import_tasks.py::StorageImportHandler`
  - `_scan_impl()` 只扫描
  - `_index_confirmed()` 确认后批量建立索引/annotation
- 状态原子转换：`platform_core/task_runtime/repository.py::resume_after_confirmation()`
- HTTP：`app.py`
  - `POST /api/v61/projects/{project_id}/storage-imports/scan`
  - `GET /api/v61/projects/{project_id}/storage-imports/{task_id}`
  - `POST /api/v61/projects/{project_id}/storage-imports/{task_id}/confirm`
- 前端请求/轮询合同：`static/modules/server-material-import.js`

### 已确认缺口与落点

- `label_mapping` 当前主要保存平台 code，正式框仍写数组位置 `class_id`；Task 1 改为稳定 `label_id`，同时保留旧 code 输入兼容。
- `ImportCandidateStore.label_mapping` 尚缺 `import_id`、类别统计/样例索引和完整确认快照；Task 1 在原 manifest 内扩展，不另建 JSON 清单。
- `static/app.js` 的 `renderImportTask()/confirmStorageImport61()` 仍是页面权威 UI，但它直接内嵌映射 HTML；Task 1 迁到 `server-material-import.js` 提供合同/视图数据，并删除对应旧 override。
- `static/modules/storage-import-progress.js` 仍有“仅 SUCCEEDED 才完成”和直接输出确认按钮的旧扫描路径；Task 1 将其重定向或删除，不能与 server import polling 并存。
- `app.py` v52 ZIP 导入/同步 `labels/remap` 属于历史导入后修标签路径；Task 1–2 收口后不得再作为新 Storage Import 的入口。

## 2. 平台标签与 Annotation

### 当前权威路径

- 项目标签兼容数据：`app.py::project_label_items()`、`ensure_label()`、`get_label_id()`。
- annotation 主库：`platform_core/annotation_repository.py::AnnotationRepository`。
- boxes 归一/摘要：`platform_core/annotations.py::normalize_boxes()`、`annotation_summary()`。
- 人工标注 API：`app.py::get_annotation()`、`save_annotation()`。

### 已确认缺口与落点

- 当前标签稳定性仍依赖 `project.labels` 数组下标，删除/前移会改变 class_id；Task 1 为 `label_meta` 补稳定 `label_id`，Task 3 让 annotation 以其为权威。
- `AnnotationRepository` 当前只有 state/boxes，尚无 `annotation_scope`；Task 3 原表迁移并兼容 legacy JSON。
- `annotations.py` 仍由 code->数组 class_id 规范化；Task 3 统一稳定 ID，同时只在任务导出时生成临时 YOLO class。
- `app.py` 中逐图 JSON/同步遍历的标签删除、重映射路径不是大规模权威实现；Task 2 使用 Durable Remap。

- Task 4 只在选材冻结后查询 annotation 统计，不把 Storage Source 变成训练数据集。

### 待收口路径

- `app.py::TrainReq` 和旧 preflight 仍出现 `selected_image_ids`、`val_image_ids` 等兼容字段；Task 4–8 统一为先冻结图片、再冻结标签、再生成 Split Manifest。
- `static/app.js` 同时存在 `submitTrain425/428/429` 等多代提交 override，且多处 `device||'cpu'`；Task 4 和 Task 8 只保留一个权威 submit schema。
- `training_tasks.py` 已显式拒绝 `train_dataset_ids/test_dataset_ids`，此防线必须保留。
- 当前快照/worker 尚未按 `annotation_scope` 判断每类别 GT，也未物理封存 Test；Task 5–6 在上述权威模块内完成。
