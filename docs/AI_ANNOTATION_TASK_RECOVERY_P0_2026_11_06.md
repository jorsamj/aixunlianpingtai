# AI 自动标注任务故障恢复与已完成结果保护 P0（42.24.540）

## 背景和目标

接续 `42.24.539`，仅处理原自动标注任务的可靠性，不重建 WeVisOne 适配、模型管理、任务中心、候选库、GT Writer 或 UI 工作台。原实现已经逐图提交 SQLite 候选数据，且能在 Worker 异常重启后从 CandidateStore 前缀恢复；但人工点击「重试」会复制完整冻结图片列表新建任务，导致已成功的图片重复推理。取消/失败任务已保存的候选，亦无回到原人工审核流程的入口。

## 本次实现

1. **原任务 ID 差量续跑**：`POST /api/v60/projects/{project_id}/annotation-tasks/{id}/retry` 对普通 AI 标注不新建任务、不清空候选库。任务恢复为 `QUEUED`；Worker 根据原冻结图片顺序、已提交的候选前缀，只重试 `failed` 行及尚无候选行。`success` 和合法 `empty` 行绝不重跑。重试前严格对比已有候选的源素材 SHA（有历史哈希的行），不允许旧坐标套用到变更图片。MATERIAL_BATCH 仍保留原任务中心的独立重试语义。
2. **每图持久化**：仍复用 CandidateStore SQLite；每个候选写入都受原 Worker lease/cancel 围栏保护，独立提交。进度 checkpoint 可滞后于 CandidateStore，恢复时以候选库的连续前缀为权威。失败行在重试成功后才被原行更新；完成行不被触碰。
3. **连续服务故障熔断**：同一轮遇到 3 次连续网络不可达/超时/服务异常/无效协议响应，停止该批次继续调用模型；模型未加载、明确协议错误、鉴权或资源不存在等确定性错误直接停止。已成功候选照常保留；有成功项则进入待审核，无成功项为环境阻塞。普通单图内容/拒识异常记录为该图失败，不应自动拖垮整批。
4. **失败/取消结果恢复审核**：`POST .../{id}/review-completed` 把已取消/失败/环境阻塞的任务中已有 `success/empty` 候选重新暴露到原 `AWAITING_CONFIRMATION` 人工审核页，不执行推理、更不自动写正式 GT。仍须用户显式确认并经原 review/confirmation/GT Owner 流程入库；失败项不进入 GT。
5. **审核保护**：重试与恢复审核复用原 `review.lock`；已被人工接受/拒绝、已有 GT 提交日志或审核确认的任务不能重新生成候选。共享 runtime 的 `CANCELLED + accepted=false` 是取消标记，不等同人工拒绝，恢复时重置 `accepted=NULL`。原任务正式提交后的 `SUCCEEDED/PARTIAL_SUCCESS` 不再提供整批重试。
6. **原界面闭环**：任务详情显示已处理、失败、待处理，显示「补跑失败/未处理」与「审核已完成部分」；列表同样提供入口。审核仍进入原独立审核页，未叠加弹窗/抽屉；前端不新增请求中心或缓存。

## 独立回归场景

- 部分成功/部分失败：第二次只调用失败图片；成功框内容完全一致，真实 GT 提交数为 0。
- 同一轮 100 张图，第一张成功、接着服务连续 3 次不可达：只调用 4 张，剩余 96 张未处理，原成功结果可审核。
- Worker 在候选 SQLite 提交后、checkpoint 写入前崩溃：原测试断言成功图片不重复推理。
- 恢复前原素材 SHA 变更：拒绝调用模型，以免使用过期坐标。
- 排队任务被取消：原任务 ID 可重入队列；包含成功候选的取消任务可进原审核页，绝不直接写 GT。
- 任务已审核/已提交：拒绝新一轮候选覆盖；通用模型、WeVisOne 接口、MATERIAL_BATCH 原回归必须继续通过。

## 运维与验收边界

- 本地验证（2026-11-06）：Python 相关跨 Worker/API/Integration/候选/WeVisOne 回归 **177/177 通过**；Node 完整前端 **1544/1544 通过**；`py_compile`/`git diff --check` 通过。扩展 Python 组合的额外 4 项失败中，1 项仍调用已正式退役的 v47 API（正确返回 410，旧断言要求 200），另外 3 项是当前隔离执行环境无法启动 `sys.executable` 子进程的 fencing 测试；这 4 项不当作通过，也没有为此放宽原接口或进程安全逻辑。
- 安全性：这是**候选级**失败恢复，保存成功不等于检测准确；人工复核后才可成为正式 GT。重复点击 retry 的并发请求受到事务状态 + 审核锁的双重阻止。
- 恢复策略：恢复审核与补跑是两个用户选项；一旦正式审核完毕，不再允许补跑原任务以免覆盖人工结果。尚未处理图片若仍需标注应另起任务。
- 生产环境：不修改 4070/A800 服务、生产模型、素材、正式 GT 或数据库。本地隔离测试与远端 GitHub CI 是软件回归，不能代替生产网络故障演练、真实 4070 大批量任务和 Chrome 三视口 UAT；这些必须单列未验收。
