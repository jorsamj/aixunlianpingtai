# v42.25 Task Runtime Fencing Design

日期：2026-09-11  
状态：IMPLEMENTED ON `refactor/v42.25-runtime`; targeted CI validation in progress; NOT MERGED; A800 REAL TRAINING NOT VERIFIED

## 1. 背景与风险

v42.24 的 Durable Task 已经有 `lease_token / lease_expires_at / worker_id`，也会周期 heartbeat，但仍存在 split-brain 执行窗口：

```text
Worker A claim task
    ↓
A 启动训练/转换子进程
    ↓
A 的 lease 过期或失去所有权
    ↓
旧 heartbeat thread 退出，但 Handler/child process 可能继续执行
    ↓
TaskRepository.release_expired() 把任务重新 QUEUED
    ↓
Worker B 再 claim
    ↓
A 与 B 同时产生副作用
```

训练、转换、部署类任务尤其危险，因为副作用包括 GPU 占用、模型产物、日志、任务最终状态和外部 SDK 子进程。

本批目标不是引入分布式数据库，而是在当前单机 SQLite/WAL 架构内建立严格 execution fencing。

---

## 2. 核心原则

### 2.1 `tasks.attempt` 作为 execution generation

每次成功 claim 时，旧 Repository 已经递增 `attempt`。

因此本批不新增数据库字段，直接定义：

```text
execution_generation = tasks.attempt
```

一个合法执行必须同时持有：

```text
task_id
lease_token
execution_generation
lease_expires_at > now
status in RUNNING / CANCEL_REQUESTED
```

旧 Worker 即使仍保存旧 token，也不能跨 generation heartbeat / bind process / finish。

### 2.2 无法证明所有权时 fail closed

以下情况均不得“继续跑着看看”：

- lease 已过期；
- token 不匹配；
- generation 不匹配；
- heartbeat 无法确认成功；
- task DB 临时不可达，无法证明续租；
- 旧进程树无法完整检查；
- 进程权限不足，无法证明已终止。

策略：

```text
cannot prove ownership
→ mark lease_lost
→ stop accepting fenced side effects
→ terminate exact bound process tree when possible
→ do not publish terminal result from stale generation
```

## 3. `FencedTaskRepository`

实现文件：

- `platform_core/task_runtime/fenced_repository.py`

生产 `task_worker.py` 使用 `FencedTaskRepository`；Web/API 仍可使用兼容的基础 `TaskRepository` 创建/读取任务，两者共用相同 SQLite schema。

### 3.1 `assert_execution`

校验：

```text
task_id
lease_token
attempt == execution_generation
active status
non-expired lease
```

失败返回 `PermissionError`，上层转换为 `ExecutionFencedError`。

### 3.2 Generation-aware mutation

以下 mutation 在生产 Worker 上校验 generation 与 lease expiry：

- heartbeat
- bind_process
- finish

旧 generation 禁止覆盖新 execution 的状态。

### 3.3 Expired task recovery hold

过期 RUNNING/CANCEL_REQUESTED 任务不再无条件 `→ QUEUED`。

如果任务记录了：

```text
process_pid
process_create_time
process_command_hash
```

先检查精确进程身份。

结果：

```text
exact process alive
→ keep RUNNING
→ stage = lease_expired_process_alive
→ do not requeue

cannot inspect safely
→ keep RUNNING
→ stage = recovery_blocked_process_inspection
→ do not requeue

exact process gone
→ safe recovery / queue

PID exists but create_time/hash mismatch
→ exact old process considered gone
→ NEVER kill unrelated reused PID
```

## 4. Recovery reaper

`reap_expired_processes()` 在 claim transaction 之外运行：

```text
find expired active tasks with persisted process identity
    ↓
ProcessController.terminate_tree(exact identity)
    ↓
only after exact old execution is verified non-executing
    ↓
release_expired may requeue/cancel
```

避免在 SQLite write transaction 内等待进程终止。

## 5. Process identity / process tree

实现：

- `platform_core/task_runtime/process_control.py`

身份：

```text
PID
create_time
command_hash(argv)
```

新增 `ProcessIdentityMismatchError`，用于区分：

- PID 被重用/命令不符；
- AccessDenied / 无法检查。

### 5.1 PID reuse

若 PID 存在，但 create_time 或 command hash 不一致：

```text
never terminate that PID
```

因为它已经不是本任务拥有的进程。

### 5.2 Process tree fail closed

无法列出 children / AccessDenied 时，不得假装“没有子进程”。

### 5.3 Descendants before root

终止顺序：

```text
known descendants
→ verify non-executing
→ root
```

理由：若先杀 root，而 GPU/SDK child 仍活着，系统可能误判旧 execution 已结束并重新调度。

### 5.4 Linux zombie semantics

`zombie` 已经不能执行代码或占用 GPU 计算，只等待父进程/系统回收。

因此安全判断是：

```text
zombie = non-executing
```

zombie 不应阻止父进程结束；真正仍在 running/sleeping/stopped 的 child 才是 execution blocker。

## 6. `WorkerContext` execution fence

实现：

- `platform_core/task_runtime/worker.py`

新增：

```text
execution_generation
lease_lost event
cancel event
assert_current_execution()
heartbeat()
finish()
bind_process()
terminate_bound_process()
```

生产路径通过 Context 进行 generation-aware mutation。

为了兼容当前 TrainingHandler 的旧写法，如果 Handler 仍直接调用 `context.repository.bind_process()`，`terminate_bound_process()` 会从 TaskRecord 恢复 persisted PID/create_time/hash，再按精确身份终止。

这只是迁移兼容；后续新 Handler 应优先使用 `context.bind_process()`。

---

## 7. Artifact publication fencing

`WorkerContext` 向 Handler 暴露 `FencedArtifactStore`。

### 7.1 Atomic JSON publish

流程：

```text
assert current execution
→ serialize to private temp
→ fsync temp
→ assert current execution AGAIN
→ os.replace(temp, final)
```

第二次校验发生在最终原子发布之前，用于缩小“序列化期间失租”的 stale publish race。

### 7.2 Logs

append log 也在真正 open/write 前再校验。

### 7.3 Known boundary

如果旧 Handler 在仍持有 lease 时拿到一个 `Path`，之后完全绕过 Context 直接写文件，Context 无法拦截已经泄漏出去的 Path。

因此后续迁移原则：

- final result / checkpoint / published artifact 必须通过 Context artifacts；
- 新 Handler 不应长期持有 raw artifact path 后绕过 Context 发布最终结果。

## 8. Scheduler behavior

实现：

- `platform_core/task_runtime/scheduler.py`

### 8.1 Lease renewal

renew thread 使用 `context.heartbeat()`。

任何无法证明 renewal 成功的异常：

```text
mark lease_lost
→ terminate bound process tree
→ stop renewal
```

不是只有 PermissionError 才停。

### 8.2 Stale result

Handler 返回结果后，在 finish 前再次 `assert_current_execution()`。

若 stale：

```text
do NOT mark SUCCEEDED
do NOT mark FAILED
terminate bound child process
leave recovery to current repository state
```

旧 generation 永远不能“最后一写赢”。

### 8.3 Before claim

每次 claim 前：

```text
reap_expired_processes()
release_expired()
claim_next()
```

## 9. Resource recovery fence

不仅要防止同一个 task 重跑，还要防止旧 execution 还占资源时，同 `resource_key` 的另一 task 进入。

若同 resource_key 存在 recovery hold：

```text
RESOURCE_RECOVERY_FENCE
→ candidate remains QUEUED/resource_waiting
```

覆盖 conversion / CPU / named resource 等普通资源。

---

## 10. GPU reservation quarantine

旧训练进程仍活着或无法证明已结束时，GPU 仍可能被其占用。

因此 recovery hold 时保留 reservation，并强制：

```text
policy = exclusive
share_eligible = false
sharing_evidence_at = null
```

同时短期续 `gpu_reservations.expires_at`，但**不续 task lease**。

目的：

- task 仍明确处于 expired recovery；
- GPU admission 不会把别的训练任务共享进同一卡；
- 等旧进程清理后，再释放 reservation。

## 11. Conversion process lifecycle

实现：

- `platform_core/deployment/conversion_tasks.py`

从旧：

```text
subprocess.Popen
process.terminate/kill parent only
```

改为：

```text
launch_process
context.bind_process
context.heartbeat
ProcessController.terminate_tree
```

lease lost / cancel 时终止整棵转换工具进程树。

本批没有改变厂商转换成功但缺硬件验证时的业务状态语义；该问题属于后续 Conversion/Deployment contract 批次。

## 14. Remaining boundary / 后续工作

本批建立 Runtime ownership fence，但不能在 Python 中强行安全终止任意正在执行的 Handler thread。

因此：

- 通过 Context 的 task/artifact/process side effects 已 fencing；
- 有外部 child process 的任务可强制终止 exact process tree；
- 纯 Python Handler 若完全绕过 Context 直接写业务数据库，仍需在批次/事务边界调用 `heartbeat / assert_current_execution`。

后续逐步要求所有长任务：

```text
small idempotent batch
→ context heartbeat/assert
→ transactional business mutation
→ checkpoint
```

不要重新引入“启动一个 daemon thread 后不再检查 lease”的执行模型。

下一批优先级：生产安全收口（`/data` 静态暴露、CORS、SSRF、训练服务器 secret）。
