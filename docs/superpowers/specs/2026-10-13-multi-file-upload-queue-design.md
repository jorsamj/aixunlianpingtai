# 多文件上传队列与任务中心修复设计

## 问题与根因

ZIP 批量入口虽然使用了全局 `createZipTransferLimiter(2)`，但任务中心登记发生在取得传输槽位、创建服务器上传会话之后。第 3 个及后续文件因此只存在于限流器等待 Promise 中，用户看不到受理状态；文件指纹又在整批登记之前完成，进一步延迟首个反馈。任务中心展开列表还固定截取前 10 条，部分入口使用空 `catch`，导致异常缺少可见结果。

普通素材上传会把本次选择的全部文件放入同一个 `FormData`，没有把并发 2 当成文件数量上限；本轮只补必要的合同回归，不引入第二套普通素材队列。

## 既有 Owner 与不变边界

- `ZipImportRuntime` 继续拥有 ZIP 浏览器传输、暂停、续传、取消和持久会话衔接。
- `UploadTaskCenterRuntime` 继续是唯一右下角任务展示 Owner。
- `createZipTransferLimiter(2)` 继续是唯一浏览器 ZIP 传输并发控制，跨批次 FIFO。
- 服务端 ZIP 正式导入继续使用现有 Durable Upload 与 FIFO Import，不新增调度器。
- 标签确认、正式素材提交、取消清理和已完成任务边界不变。

## 修复设计

1. 文件选择后立即逐文件建立本地任务身份并写入任务中心；合法文件显示“等待上传”，非法文件显示具体失败原因。
2. 所有合法文件按选择顺序立即加入现有限流器。前两个取得槽位，其余保留可见排队序号；一个文件失败或取消不影响后续文件取得槽位。
3. 文件指纹可并行准备，但不能阻止任务中心首屏反馈。批内重复文件按文件显示失败，不让其他有效文件消失。
4. 取得槽位后，把本地任务更新为准备/上传状态；服务器返回 Upload ID 后通过任务中心 `rekey` 原地切换为持久身份，继续复用现有暂停、续传、安全取消与清理合同。
5. 等待上传任务支持本地取消；它没有服务器资源，只取消自身。已创建 Upload ID 的任务继续调用现有服务端取消。
6. 任务中心显示全部活动任务，终态历史受有界保留策略控制；摘要分别显示上传中和排队数量。展开列表固定高度滚动，逐项显示名称、大小、状态、真实进度、排队序号、错误及可用操作。
7. 刷新后，本地 File 对象不可恢复的任务转为“需要重新选择文件”；已建立服务器会话的任务仍按现有续传合同恢复。
8. 项目切换清理当前运行时的本地排队控制，避免跨项目启动；持久任务继续按项目隔离存储。

## 验收重点

- Chrome 中选择 3、5、10 个 ZIP 后立即出现等量任务。
- 同时实际传输的 ZIP 不超过 2 个；跨批次仍按统一 FIFO 推进。
- 排队取消、传输失败、标签等待、最小化和刷新均有明确状态。
- 普通素材入口仍提交选择的全部文件。
- `VERSION.txt` 升级为 `42.24.356`，并只更新本轮相关静态资源缓存键。
