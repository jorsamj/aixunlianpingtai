# 训练任务数字优先级设计

## 目标

训练任务创建时允许用户填写 `1–999` 的数字优先级。`1` 为最高优先级，数字越大优先级越低；同一训练资源内，相同优先级的任务按进入队列时间先后执行。

本设计只覆盖需求第 1 项“优先级排序”。运行中任务抢占、完整插队、暂停、停止和继续分别在后续独立设计与实现。

## 当前问题

现有页面只提供“普通、优先、最高”三个选项，分别保存为 `50、80、100`。现有调度器按数字从大到小执行，与新规则完全相反。直接修改排序方向会让历史排队任务顺序颠倒，也会让现有插队接口把任务排到更后面。

## 用户界面

- 创建训练任务的“任务优先级”改为数字输入框。
- 输入范围为 `1–999`，默认值为 `50`，步长为 `1`。
- 输入框下方固定显示：`1 最高，数字越大优先级越低；相同数字按进入队列时间排序。`
- 训练任务列表显示 `优先级 N`。
- 排队任务继续显示同一训练资源内的队列名次。
- 非法值在提交前直接提示，不发送训练请求。

## 接口与数据

新建训练任务继续使用 `queue_priority` 字段，避免破坏已有接口，但新增：

```json
{
  "queue_priority": 50,
  "priority_scheme": "lower_number_first"
}
```

后端要求 `queue_priority` 必须为整数且位于 `1–999`。缺省值为 `50`。任务持久化时写入 `priority_scheme=lower_number_first`，任务列表响应保留这两个字段。

## 调度规则

调度只在同一训练资源内比较任务：

1. `queue_priority` 数值小的任务先执行。
2. 数值相同则按 `queued_at` 升序执行。
3. `queued_at` 缺失时使用 `created_at`。
4. 排序仍相同则以任务 ID 作为稳定排序的最后条件。

正在运行的任务不会因为新任务优先级更高而在本需求中自动暂停或被抢占；运行中抢占属于需求第 2 项。

## 历史任务兼容

历史任务没有 `priority_scheme`，其常规取值来自旧页面：

- 旧 `100（最高）` 转换为新 `1`。
- 旧 `80（优先）` 转换为新 `20`。
- 旧 `50（普通）` 转换为新 `50`。

只迁移仍处于 `queued` 状态的历史任务，并在任务文件中写入新字段。已完成、失败或停止的历史记录保持原值，避免改写审计历史。

旧插队接口在本次修改中只做排序方向兼容，确保不会因为新规则把任务排到更后；“插到哪一位”和“是否抢占运行任务”在需求第 2 项中完善。

## 错误处理

- 布尔值、小数、文本、空字符串、`0`、负数及大于 `999` 的值由后端拒绝。
- 前端提交前再次检查整数范围，并显示明确中文提示。
- 历史任务缺少优先级时按默认值 `50` 迁移。
- 单个历史任务迁移失败不得阻止其他任务调度；失败信息写入服务日志并按兼容排序值处理。

## 测试

- API 测试：接受 `1、50、999`，拒绝非法值。
- 调度测试：优先级 `1` 在 `2` 前执行，`2` 在 `50` 前执行。
- 稳定性测试：相同优先级按排队时间执行。
- 资源隔离测试：不同训练资源的优先级互不影响。
- 历史兼容测试：旧 `100、80、50` 的活跃排队任务迁移后保持“最高、优先、普通”的相对顺序。
- 浏览器测试：创建弹窗显示数字输入、默认 `50` 和规则提示，并把用户填写值传给后端。
- 浏览器测试：训练任务列表显示优先级和正确队列名次。

## 不在本次范围内

- 自动暂停正在运行的低优先级任务。
- 用户指定某个精确队列位置。
- 暂停、停止后的检查点保存与继续训练。
- 跨训练资源的全局队列排序。
